- **#2** — The decide step checks `if (listing.status === 404) return yield* Effect.log('main has no scorecard workflow yet: first baseline')` before calling the `ok()` filter. The `ok()` function (line 154) rejects all non-2xx responses with `GithubApiError`, so a 401/403/429 from the GitHub API (token revoked, rate limit, org membership changed) fails the run instead of treating it as a missing baseline and proceeding with a first-baseline ratchet. A transient auth error turns every PR into a hard CI failure instead of "no baseline, build your first pipeline" silent pass.

  **Suggested fix:** Move the 404 short-circuit to happen before `ok()` is called, treating both 404 and 401/403 as "no baseline, first baseline". Or have `ok()` swallow 404/401/403 specifically.

- **#4** — The scorecard job runs once per PR and downloads main's most recent successful scorecard artifact via `actions/runs` API. With two PRs open simultaneously (both targeting the same main SHA), both runs download the same stale main artifact and both pass the ratchet against it. The first merge triggers a new push to main which produces a new artifact; the second merge has already passed its gate against the pre-merge version. There is no serialization across PR->merge transitions in `concurrency: scorecard-${{ github.ref }}`; each PR ref is independent. The ratchet silently misses regressions across concurrent merges within the same minute.

  **Suggested fix:** Add a required-status-check that re-runs the scorecard workflow against a synthetic merge commit (a CI job that merges PR head into main tip and grades the result). Until that exists, document the silent window in AGENTS.md and require serial PR merges during bootstrap. Note this does not affect PRs from forks that rebase to current main.

- **#6** — `scorecard ci` (src/main.ts:179,184) gates both cache-restore and cache-save on `decide(['cache-check', '--file', ...]) === 0`. A cache entry holding an `InstrumentError` cell must return exit 1 to refuse the cache; a clean entry must return exit 0. The PR rules table names this as proof ("cache-check on a poisoned entry... exit 1"), but no automated journey or vitest property covers it. The J3 aggregate journey exercises a clean fixture; the `cache-check` path through `FamilyResultSchema` decode and the `CacheUnusable` filter is unobserved.

  **Suggested fix:** Either add a journey entry to `journeys/manifest.json` for cache-check (clean and poisoned cases), or add a vitest integration building a `FamilyResult` with an `InstrumentError` cell and asserting `cacheCheck(['--file', ...])` exits with `CacheUnusable`. Match the J3 journey pattern.

- **#9** — The property `rows compared with themselves fail only where the verdict is an instrument error` compares rows to themselves and asserts `ids(ratchet.failures) === ids(rows.filter((r) => !passing(r.verdict)))`. Both `Held` and `New` outcomes produce empty failures, so a bug that returned `_tag: 'New'` instead of `Held` (or `FirstBaseline` instead of `Compared`) would pass. The other compareWithMain properties cover LostBeaten/ReBaselined/Regressed/Neutral/InstrumentError specifically; the Held happy path is left with only this imprecise oracle.

  **Suggested fix:** Tighten the assertion to also check `ratchet._tag === 'Compared' && ratchet.outcomes.every((o) => o._tag === 'Held')` alongside the failures check.

- **#10** — The property `without a main artifact the ratchet is a first baseline failing only instrument errors` compares rows to a Missing main and asserts failures match. It does not assert that every outcome `_tag === 'New'` or that `ratchet._tag === 'FirstBaseline'`. A bug where `unlessInstrumentError` returned `Held` (which is also not a failure) would not be caught; both `New` and `Held` produce empty failures for passing verdicts.

  **Suggested fix:** Extend the assertion to require `ratchet._tag === 'FirstBaseline' && ratchet.outcomes.every((o) => o._tag === 'New')` alongside the existing failures check, matching the pattern as #9.

- **#11** — `starterAgainstMainMeasurement` returns `regressed(main, pr)` for `pr.starter.cell._tag === 'Unsupported'`, but no compareWithMain property test exercises a PR starter cell that was `Measured` on main and is now `Unsupported`.   **Suggested fix:** Add a property that constructs a main with `starter: Measured(runs)` and a PR with `starter: Unsupported { citation, check: Verified }`, and asserts `ratchet.failures.length === 1 && ratchet.failures[0]._tag === 'Regressed'`.

- **#12** — `compare-with-main.workflow.ts:56` maps `pr.starter.cell._tag === 'InstrumentError'` to a row-level InstrumentError outcome, but this combination is untested. The property tests construct PR rows via `withStarter(main, cell)` which preserves the verdict from main; when the main verdict is non-error and the PR cell is InstrumentError, this branch emits the expected outcome, but no property test exercises that specific case.
