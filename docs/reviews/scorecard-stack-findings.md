| 4 | `evals/ratstack-scorecard/src/model/judge-row.workflow.ts:73` | Aggregate treats a rat-stack `Unsupported` cell with `Verified` citation as a guaranteed `Beaten`, masking instrument errors in starter | adversarial       | 50         |

- **#1** — CONST-T12 forbids the runner from classifying tests by filename suffix; renaming `static.journey.test.ts` to `static.test.ts` would silently move it from the journeys project into the model project, run it without the sandbox and the subprocess it depends on, and turn the test count green while the journey is no longer covered. The harm the rule exists to catch — fragile, name-coupled test discovery — is exactly what the current include glob produces. **Decision required:** either drop the `*.journey.test.ts` suffix from the journeys include glob and signal journey identity through file location or imports, or declare the CONST-T12 breach explicitly per CONST-W3.

- **#2** — The measure job always restores the rat-stack side from `actions/cache` keyed by `scorecard-ratstack/<family>/rat-stack=<sha>/instrument=<tree>/nixpkgs=<rev>`. A PR whose `instrument` hash equals the cached main run's instrument hash (which is the common case, since `instrumentHash` is `HEAD:evals/ratstack-scorecard`) will reuse the rat-stack side measured on main. The starter side, however, is always measured afresh. If the cached rat-stack artifact silently contains an `InstrumentError` cell (e.g. from a previous run where the sandbox had a flaky parse failure), the aggregate job uploads a `family-<name>` artifact that combines a broken rat-stack result with a freshly measured starter. The `judgeRow` decision then propagates the stale measurement into the ratchet. **Decision required:** either (1) drop the cache and measure both sides every run (the KTD7 cold posture), or (2) when restoring from cache, re-validate the cached artifact by reading it and rejecting it if any `_tag === 'InstrumentError'` is present. The fix should be matched to the KTD7 ruling; document the choice in a CONST-W3 declaration if it diverges.

- **#3** — Test files are partitioned into projects by filename suffix (vitest.config.ts:5 declares `src/**/*.test.ts` as a separate `model` project); this violates CONST-T12, which forbids classifying tests by filename suffix. **Decision required:** either declare the CONST-T12 breach explicitly in the PR description per CONST-W3, or collapse the two projects into one with no filename-based partition: include both globs in one project and distinguish model vs journey via tags or by what the test imports.

- **#4** — When rat-stack's side is `{_tag: 'Unsupported', citation, check: Verified}`, `judgeRow` calls `againstStarter(input, { measured: () => beaten, unsupported: tie })`. The `measured` branch is reached only when the starter is also `Measured`. When the starter is `Unsupported` or `Unmeasurable`, the verdict becomes `Tie`. When the starter is `Absent`, the verdict is `NotBeaten`. When the starter is `InstrumentError`, the verdict is an `InstrumentError`. The defect: when rat-stack's `Unsupported` citation is `Verified` and the starter is `Measured` with values that would normally be `Beaten`, the verdict is `Beaten` without invoking `compareRuns`, so a starter `InstrumentError` or `Unsupported` cell cannot override the verdict. This is consistent with KTD1 ('beaten only when the starter's worst run is strictly better than rat-stack's best run') only by an implicit 'no rat-stack value to beat' reading. **Decision required:** either (1) add a comment that `Unsupported` rat-stack rows are `Beaten` only because no comparison is possible, and add a property test for `direction='higher'` on counts to lock the assumption, or (2) apply `compareRuns` against the citation's last-known value so the rule holds uniformly.

- **#5** — The pin job runs `scorecard pin check`, which shells out to `git ls-remote https://github.com/joelhooks/rat-stack refs/heads/main`, parses the SHA out of the response, and feeds it into `planPinBump`. If a transient GitHub fetch delay returns a 200 with an empty body (or `git ls-remote` outputs the symmetric case where the SHA line is split across multiple writes), `string(remote.split(/\\s/u)[0], ...)` will hand an empty string to `planPinBump`, which returns `PinMoved` because `'' !== pinned`. The job then `git switch -c scorecard/pin-rat-stack && git push --force` on the pin file. That force-push can overwrite an in-flight human-authored PR on the same branch. **Decision required:** guard the PinMoved path with a SHA shape check (`/^[0-9a-f]{40}$/.test(to)`) before opening a PR; if the shape is bad, exit the pin job as `PinCurrent`-equivalent (logged as a fetch problem, not a pin bump).

- **#6** — The pin-bump job constructs the push URL as `https://x-access-token:${GH_TOKEN}@github.com/${GITHUB_REPOSITORY}.git` and passes the literal URL (with the token) as the first argument to `git push --force`. The token is a short-lived GitHub App installation token with `contents: write` and `pull-requests: write` on this repository. Anything that captures the running process's argv — the runner process list, core dumps, any future `set -x` or ACTIONS_STEP_DEBUG, and the .git/config remote URL after the push — sees the token. Anyone reaching the runner (including a side-channel via a compromised rat-stack pinned at the time the job runs) can lift the token. This is a canonical CWE-798 (Use of Hard-coded Credentials) / CWE-532 (Insertion of Sensitive Information into Log File) exposure. **Fix required:** do not place the token on the command line. Configure a credential helper via 'git credential approve' (write the protocol/host/token to a tempfile), then push the URL without credentials; or use a deployment key bound to 'scorecard/pin-rat-stack' only. Independently consider narrowing the App token to 'pull_requests: write' only and using a separate deployment key for force-push.

- **#8** — If api.github.com stalls (slow 5xx, partitioned network, DNS hang), the aggregate job waits up to its 30-minute workflow timeout, wastes a full runner, and produces no scorecard.json / ratchet decision for the run — every PR to main loses its scorecard signal for that day. The protection is reachable: the same module already uses `AbortSignal.timeout` for sandboxed subprocesses (harness/sandbox.ts:36) but not for the fetch boundary. **Fix required:** add a signal option to the fetch call: `{ headers: …, signal: AbortSignal.timeout(15_000) }` (15s is generous for a list-runs call) and surface the timeout as a 'no-baseline' (empty stdout) response — same shape as the existing 404 handling — so a GitHub outage degrades to first-baseline rather than wedging the job.

- **#9** — The ratchet's `compareRow` returns `{_tag: 'ReBaselined', id}` whenever `main.definitionHash !== pr.definitionHash`. This is the intended escape hatch for a changed metric: the row is dropped from the comparison and treated as a new baseline. But the same flag fires for a definitionHash that diverges because of a _different_ family cache key, a different nixpkgs rev, or even whitespace differences in the `registry.ts` JSON stringify. A PR that adds a single comment to `src/families/static.ts` invalidates the cache key (good) AND every definitionHash (because `trees` records `HEAD:evals/ratstack-scorecard/src/families/static.ts`). The whole scorecard is re-baselined invisibly. **Decision required:** either (1) restrict `definitionInputs` to the actual metric-defining files (e.g. `registry.ts` + the `family` impl, not `src/tools` and `src/harness`), or (2) emit a visible 'definitionHash drift' warning in the Markdown summary so the re-baseline is observable in the job output.
